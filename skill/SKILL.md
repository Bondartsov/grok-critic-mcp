# Grok Critic — внешний критик

## Что это

MCP-сервер `grok-critic` оборачивает модель `grok-4.20-multi-agent` (xAI, через Polza.AI): несколько независимых reasoning-агентов анализируют задачу параллельно и сходятся к консенсусу. Это **второе, независимое мнение** — агент, писавший код, не должен быть его единственным ревьюером.

Универсальный скилл для любых MCP-клиентов (Kilo Code, ZCode, Claude Code, Cursor). Клиент-специфичные места помечены.

## Когда вызывать

| Ситуация                                                         | Инструмент            |               Приоритет                |
| ---------------------------------------------------------------- | --------------------- | :------------------------------------: |
| Завершено планирование / архитектура / system-design             | `architecture_review` |              Обязательно               |
| Написан существенный код (> 50 строк)                            | `critic_review`       |              Обязательно               |
| Баг-фикс не удался с первой попытки                              | `critic_review`       |              Обязательно               |
| Security-чувствительный код (auth, payments, crypto, user data)  | `security_audit`      |              Обязательно               |
| Перед merge / PR                                                 | `critic_review`       |             Рекомендуется              |
| Спорное архитектурное решение                                    | `architecture_review` |             Рекомендуется              |
| Тривиальные правки (rename, форматирование, < 10 строк)          | —                     |    **Не вызывать** — вызов платный     |
| Только что сгенерированный тобой код, который ты ещё не прочитал | —                     | **Не вызывать** — сначала прочитай сам |

## Инструменты

### Ревью (платные — к модели)

```
critic_review(content, context?, agent_count?, focus_areas?, output_format?, file_path?)
architecture_review(content, context?, agent_count?, file_path?)
security_audit(content, context?, agent_count?, file_path?)
critic_followup(question, previous_review?, review_id?, agent_count?)
```

Ключевые правила параметров:

1. **Всегда передавай `context`** — проект, язык, назначение. Без контекста критик работает вслепую.
2. **Всегда задавай `focus_areas`** для `critic_review` — `"security,performance,SOLID"` вместо размытого «посмотри вообще».
3. **Followup: `review_id` вместо `previous_review`.** В metadata каждого ревью есть `Review ID` — передай его, и сервер восстановит диалог сам (экономия ~25k input-токенов ≈ $0.065 за вызов). Полный текст — только fallback после рестарта сервера. Передавать оба параметра нельзя.
4. **`agent_count`**: `4` — быстро (~30 с, мелкие сниппеты), `16` — глубоко (~2–3 мин, архитектура/security). По умолчанию 16 из конфига; для быстрых проверок явно ставь 4.
5. **`file_path`** — путь вместо `content`; сервер сам прочитает файл (context авто = `File: <путь>`). По умолчанию **выключен** (SEC-03): статус — `reload_config_tool` (строка `allow_file_path`), разрешённые корни — `POLZA_ALLOWED_READ_DIRS` в `.env` (разделитель `;` на Windows). Секреты (`.env*`, `*credential*`, `id_rsa*`, `*.pem/*.key`, `.git/config`…) блокируются всегда — это правильно, не обходить.
6. **`output_format="json"`** — когда находки нужно обработать программно: строгий JSON `{"summary", "findings":[{severity, title, location, description, recommendation}]}`. Для обычного ревью не нужен.

### Административные (бесплатные)

```
check_health()            # статус, баланс ₽, суточный расход («Today: N calls | $X | ₽»)
reload_config_tool()      # горячая перезагрузка .env после изменения POLZA_* (без рестарта)
restart_server(reason?)   # жёсткий выход; клиент поднимет процесс сам
self_update()             # git pull + pip install + рестарт; выключен по умолчанию, требует git-клона
```

## Формат ответа

Каждое ревью = текст + metadata footer:

```
---
⏱ Elapsed: 63 s
📊 Metadata: model=… | agents=16 | effort=high
📈 Tokens: input=… output=… total=…
🧠 Reasoning: … (~4x cost)
💾 Cached: … (дешевле)
💰 Cost: 7.59 ₽ | $0.2240
🏷️ Review ID: rev_0715e81bba24   ← сохрани для followup
```

Пока ревью выполняется (1–3 мин), сервер шлёт heartbeat-уведомления — «тишина» ≠ зависание.

## Workflow

**Post-implementation review:** `critic_review` → все 🔴 исправить ДО следующей задачи → перечитать спорные пункты → не согласен — `critic_followup(review_id=…)` с аргументами. Критик пересматривает оценку при сильных аргументах. **Не глотай замечания молча.** Если 2 followup не привели к согласию — прими решение сам и зафиксируй его в итоговом отчёте с формулировкой критика.

**Architecture validation:** `architecture_review` (план/диаграмму, не только код) → followup с контраргументами («а если event sourcing вместо…?»).

**Security audit:** `security_audit` → все 🔴 исправить обязательно, 🟡 — до продакшена. Найденное по security попадает в финальный отчёт задачи.

**Обязательное замыкание:** найденные критиком 🔴 и итог спора отражаются в отчёте задачи (секция «Проверки/Открытые вопросы») — молча закрытый критик хуже отсутствующего.

**Если MCP недоступен:** гейт ревью не отменяется, и ты **не бессилен** — у критика есть CLI (команда `grok-critic`, работает из Bash/PowerShell без MCP):

```
grok-critic health          # жив ли конфиг (мгновенно, без сети); --ping — с балансом
grok-critic doctor          # диагностика: .env, ключ, сеть, store, версии + подсказки
grok-critic review <файл|-> --agents 4         # ПОЛНОЦЕННОЕ ревью в обход MCP
grok-critic followup "вопрос" --review-id <id> # диалог по review_id (store на диске)
grok-critic logs --tail 50  # сам читай, почему сервер отвалился
```

Порядок действий при сбое: `grok-critic health` → `grok-critic doctor` → если API жив, делай ревью через `grok-critic review` из Bash (это тот же критик, тот же store) → в конце попроси пользователя переподключить MCP (кэш схемы tools живёт одну сессию).

В клиентах без CLI — субагент `reviewer` (ZCode, read-only перепроверка альтернативным взглядом) либо второй проход самопроверки по чеклисту (баги/edge-cases, SOLID, безопасность, недостающие тесты) с фиксацией в отчёте.

## Стоимость и лимиты

- Типовой вызов: 4 агента ≈ $0.02–0.09, 16 агентов ≈ $0.15–0.25. Followup по `review_id` заметно дешевле followup с полным текстом.
- `check_health` показывает суточный расход — перед серией вызовов взгляни; при низком балансе предупреди пользователя.
- Защита от перерасхода на сервере: дневной бюджет (`POLZA_DAILY_BUDGET_USD`), semaphore одновременных запросов, in-flight dedup (параллельный дубль того же контента не платит дважды), retry-дедлайн (суммарное время ≤ таймауту MCP-клиента).

## Ошибки (на русском)

| Сообщение                              | Что делать                                                                                                |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| `Ошибка авторизации: …`                | Ключ невалиден — проверить `POLZA_API_KEY`                                                                |
| `Недостаточно средств: …`              | Пополнить баланс Polza.AI, предупредить пользователя                                                      |
| `Превышен лимит запросов`              | Подождать и повторить; при повторе — `agent_count=4`                                                      |
| `Превышен дневной бюджет`              | Сообщить пользователю; лимит правится в `.env` + `reload_config_tool`                                     |
| `review_id не найден`                  | Сервер перезапускался (store in-memory) — передай `previous_review` явно                                  |
| `file_path отключён` / `Access denied` | Файл вне `POLZA_ALLOWED_READ_DIRS` или в denylist секретов — передай `content` напрямую или расширь корни |
| MCP недоступен                         | Замена гейта — см. «Если MCP недоступен»                                                                  |

## Жёсткие правила

1. Критик — **дополнение к самопроверке, не замена**: сначала прочитай свой код сам, потом зови критика.
2. 🔴 CRITICAL — блокер: не переходить к следующей задаче с открытым критическим замечанием.
3. Читай ответ **полностью** — критик находит и то, что не просили.
4. Один вызов на осмысленную единицу работы (модуль/фича), а не на каждый чих.
5. Спор — аргументами через `critic_followup`, не переписыванием ревью «как хочется».

## Установка (скилл глобально из репо)

Мастер-копия этого файла живёт в репозитории (`skill/SKILL.md`) — джанкшен/симлинк из скилл-директории клиента обновляет скилл вместе с `git pull` / `self_update`, без ручного копирования.

**Windows (junction, без прав администратора):**

```powershell
# ZCode
New-Item -ItemType Junction -Path "$env:USERPROFILE\.zcode\skills\grok-critic" -Target "<repo>\skill"
# Kilo Code (заменить устаревшую копию)
New-Item -ItemType Junction -Path "$env:USERPROFILE\.kilocode\skills\grok-critic" -Target "<repo>\skill"
# Agents
New-Item -ItemType Junction -Path "$env:USERPROFILE\.agents\skills\grok-critic" -Target "<repo>\skill"
```

**Копирование (если junction невозможен):** `cp skill/SKILL.md ~/.kilocode/skills/grok-critic/SKILL.md` — но копия устаревает при обновлении сервера.

**Правила агента** (когда вызов обязателен) добавь в instructions/AGENTS.md клиента:

```markdown
## Критик (grok-critic MCP)
Обязателен при: планировании архитектуры, баг-фиксе со 2-й попытки, после > 50 строк кода, для security-кода.
```
